* DAY 3 — HANDS-ON CI/CD + CLOUD DEPLOYMENT

** Objectif

Transformer notre Loan Approval App en application testée et construite automatiquement.

Flux cible :

#+BEGIN_EXAMPLE
Code Change
→ Git Push
→ GitHub Actions
→ Tests
→ Quality Gate
→ Docker Build
→ Container Registry
→ Cloud Run
→ Health Check
#+END_EXAMPLE

** 1. Préparer l'environnement local

#+BEGIN_SRC bash
python -m venv .venv
source .venv/bin/activate

pip install -r requirements.txt
#+END_SRC

Sous Windows PowerShell :

#+BEGIN_SRC powershell
python -m venv .venv
.venv\Scripts\Activate.ps1

pip install -r requirements.txt
#+END_SRC

#+BEGIN_SRC bash

#+END_SRC

└── metrics.json

#+BEGIN_SRC bash

#+BEGIN_EXAMPLE

** 5. Faire volontairement échouer un test

Dans :

#+BEGIN_EXAMPLE

#+END_EXAMPLE

#+END_SRC

en :

#+BEGIN_SRC python

#+END_SRC

Puis :

#+BEGIN_SRC bash
pytest -v
#+END_SRC

#+BEGIN_EXAMPLE

Question :

Pourquoi voulons-nous qu'un pipeline CI s'arrête dans cette situation ?

Remettre ensuite le seuil à :

#+BEGIN_SRC python
0.50
#+END_SRC

** 9. Comprendre le workflow CI

Fichier :

#+BEGIN_EXAMPLE
.github/workflows/ci.yml
#+END_EXAMPLE

Pipeline :

#+BEGIN_EXAMPLE
Checkout
→ Setup Python
→ Install Dependencies
→ Train Workshop Model
→ Pytest
→ Quality Gate
→ Docker Build
#+END_EXAMPLE

Le workflow se déclenche sur :

#+BEGIN_EXAMPLE
push main
OU
pull_request main
#+END_EXAMPLE

GitHub recommande explicitement de configurer la version Python dans le workflow plutôt que de dépendre de la version présente par défaut sur le runner.

** 10. Provoquer un échec du CI

Créer une branche :

#+BEGIN_SRC bash
git checkout -b break-the-api
#+END_SRC

Dans :

#+BEGIN_EXAMPLE
api/main.py
#+END_EXAMPLE

modifier temporairement :

#+BEGIN_SRC python
return {"status": "ok", "model_loaded": True}
#+END_SRC

en :

#+BEGIN_SRC python
return {"status": "broken", "model_loaded": True}
#+END_SRC

Puis :

#+BEGIN_SRC bash
git add api/main.py

git commit -m "Break health endpoint"

git push -u origin break-the-api
#+END_SRC

Créer une Pull Request.

Observer :

#+BEGIN_EXAMPLE
GitHub Actions
→ test_health
→ FAIL
#+END_EXAMPLE

Le CI vient d'empêcher une modification cassée de passer silencieusement.

** 11. Corriger et relancer

Remettre :

#+BEGIN_SRC python
return {"status": "ok", "model_loaded": True}
#+END_SRC

Puis :

#+BEGIN_SRC bash
git add api/main.py

git commit -m "Fix health endpoint"

git push
#+END_SRC

GitHub relance automatiquement le workflow.

Résultat attendu :

#+BEGIN_EXAMPLE
PASS
#+END_EXAMPLE

** 12. Tagger une image avec le commit

Dans GitHub Actions :

#+BEGIN_SRC yaml

  -t loan-approval-api:${{ github.sha }} \
  .
#+END_SRC

Principe :

#+BEGIN_EXAMPLE

→ Docker Image Tag
#+END_EXAMPLE

Cela améliore la traçabilité.

** 14. Prérequis GCP

Créer un projet GCP et activer au minimum :

#+BEGIN_SRC bash
gcloud services enable \
  run.googleapis.com \
  artifactregistry.googleapis.com \
  iamcredentials.googleapis.com
#+END_SRC

Créer le repository Docker :

#+BEGIN_SRC bash
gcloud artifacts repositories create mlops-images \
  --repository-format=docker \
  --location=us-central1
#+END_SRC

** 15. Authentification GitHub → GCP

Pour le hands-on, préférer Workload Identity Federation plutôt qu'une clé JSON longue durée.

Le workflow attend :

#+BEGIN_EXAMPLE
GCP_PROJECT_ID

GCP_WORKLOAD_IDENTITY_PROVIDER

GCP_SERVICE_ACCOUNT
#+END_EXAMPLE

Les valeurs sensibles ou spécifiques à l'environnement ne doivent pas être écrites directement dans le code.

** 16. Service Cloud Run public pour le workshop

Le workflow fait un health check HTTP après le déploiement.

Pour simplifier le workshop, rendre le service public une seule fois au niveau de la configuration Cloud Run.

Ne pas utiliser le pipeline CI/CD pour modifier continuellement la politique d'accès du service.
